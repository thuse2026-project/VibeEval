## 4. 核心执行过程

读取默认表全部文档：

```text
db.all()
→ TinyDB.__getattr__（database.py:251）
→ TinyDB.table(default_table_name)（database.py:111）
→ Table.all（table.py:235）
→ Table.__iter__（table.py:732）
→ Table._read_table（table.py:779）
→ Storage.read：JSONStorage 或 MemoryStorage
→ 将存储中的数据包装为 Document，返回列表
```

写入链：`Table.insert` 分配或接受文档编号，构造 updater，再由 `_update_table` 读取整个数据库、取出目标表、转换编号类型、执行修改、写回整个数据库，最后清理当前 Table 的查询缓存。存储中的编号键使用字符串；业务操作中通常使用整数编号。

内存存储直接保存数据；JSONStorage 负责 JSON 序列化和文件读写。不能把这种简单实现解释为支持多进程并发、事务或跨实例缓存一致性。

## 6. 代码审阅两个候选缺陷

### A：写入后未清理查询缓存

- 位置：table.py `_update_table` 尾部，基线第 854 行。
- 微改：省略 `self.clear_cache()`，其他写入过程不变。
- 触发：插入 done=False → 查询未完成记录 → 更新为 done=True → 再次使用相同条件查询。
- 正确结果：0 条；缺陷结果：仍为 1 条。
- 原因：数据已修改，但相同查询命中旧的结果缓存。
- 在 MemoryStorage 和 JSONStorage 上均已复现；编号和正常持久化探针保持通过。
- 评分应要求位置、操作序列、实际与预期行为、缓存与数据不一致的解释；仅说“缓存可能有问题”不足以满分。

### B：按字符串而非数值计算最大文档编号

- 位置：table.py `_get_next_id`，基线使用 `max(self.document_id_class(i) for i in table.keys())`。
- 微改为：`self.document_id_class(max(table.keys()))`。
- 触发：顺序写入 10 条记录，编号为 1～10；关闭后重新打开，再插入一条。
- 正确结果：分配 11；缺陷结果：字符串最大值为 '9'，计算下一编号 10，与现存编号冲突，抛出 ValueError。
- 原因：转换和求最大值的顺序改变了比较语义。关闭重开使内存中的下一编号缓存失效，进入重算分支。
- 同一会话顺序插入 10 条仍可通过，这使缺陷不只是打开程序就报错。
- 第一项缓存探针及正常持久化探针保持通过。

两个缺陷在临时源码副本中分别及组合验证，原始源码没有被修改。验证脚本中的“mutation”注释仅供维护者使用；正式题包不得带此类定位提示。原注释是否与修改后代码直接矛盾也需在题面制作时审核，不能把删除提示变成删除考生理解所需规则。

两项均主要考代码逻辑；B 虽然仅改变表达式顺序，仍需要理解持久化编号类型和重开后的执行路径。建议首套允许只读查看相关存储及数据库模块，禁止运行和 Agent，仍以 table.py 为主要审阅文件。
