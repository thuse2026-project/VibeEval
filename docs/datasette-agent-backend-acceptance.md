# Datasette 两题 Agent 后端验收

用「补齐列统计」和「筛选与分页」跑完两次从读题到手动交卷的流程。验收 Agent 能否在同一个考生工作区里读文件、切换模式、申请审批、执行测试、修改代码并把真实结果反馈出来。评分、评分数据的去向和正式考试规则留到下一轮。

## 准备

1. 使用实际模型和 Linux 上的考生沙箱，固定平台提交、模型配置和两题镜像。优先复用已有的 Datasette 私有联测部署和起始镜像。另起部署时，从联测环境取得两个起始镜像和配套的工作区清单，沿用 `VIBEEVAL_DATASETTE_CONTEXTS`、`VIBEEVAL_DATASETTE_COLUMN_IMAGE` 和 `VIBEEVAL_DATASETTE_FACET_IMAGE`，用 `examples.datasette_preview:create_preview` 启动预览。每次完整复跑用新凭证及全新的两个起始工作区，避免时间到后自动交卷。
2. 从「考生入场」进入，点「准备环境」，就绪后点「开始作答」。确认 README 能在编辑器加载。每道题各开一个新 Agent 对话，题内所有提示词沿用同一个对话，以便覆盖跨轮和切换模式。
3. 开始前用工作区读取接口保存各发布文件的内容哈希，至少核对允许修改的文件和公开测试的哈希。每一步只批准符合该步要求的命令或补丁。审批前核对实际命令和目标路径。

所有运行测试的步骤都在题目工作区根目录用 README 的命令：

```sh
python -m unittest discover -s tests -p "test_*.py" -v
```

起始镜像基线是第一题 1 项失败、第二题 2 项失败。两题均应实际运行到业务断言。出现找不到 Python、导入失败、依赖缺失或工作区错误时，先恢复测试环境。 [列统计公开测试](../problems/datasette-r2/column-statistics/test_public.py) · [筛选与分页公开测试](../problems/datasette-r2/facet-pagination/test_public.py)

## 模型配置与开联测场次

复用私有联测服务时，模型由服务端统一配置。访问联测服务的 `/r2-preview/model`，返回 `{"configured":true}` 表示服务端已加载模型名和 API Key。测试员只需领考生入场凭证。另起服务时，由有权限的维护者在后端进程环境或仓库根目录的本地 `.env` 配置 `LLM_API_KEY`、`LLM_MODEL` 和所用提供商的 `LLM_BASE_URL`。真实 Key 通过服务端的私有配置管理。

当前预览使用预设的 Datasette 两题流程。开一轮联测由维护者在服务端发新的考生入场凭证。登录联测服务器，在 `backend/` 目录使用预览后端相同的 Python 和 PostgreSQL 连接配置运行：

```sh
python -m app.exams.provision \
  --candidate-id r2-check-01 --name "联测考生" \
  --exam-id datasette-agent-acceptance --title "Datasette Agent 联测" \
  --duration-minutes 120 --valid-hours 24
```

同一场次每次复跑用新的 `--candidate-id`，同一组联测可沿用 `--exam-id`。把命令输出的 `tok_…` 私下发给对应测试员。用实际预览地址的 `/entry?mode=r2` 入场。若浏览器还在恢复旧会话，用新浏览器配置或无痕窗口。预览会在首次入场后自动关联两题。网页 Agent 面板的「＋」用于在当前题里开新对话。

## 第一题 · 业务拓展 · 补齐列统计

**1. 只读计划。** 选择「只读计划」，发送：

> 请先读根目录的 README.md，再看公开测试和 datasette/views/table.py 里和题目有关的部分。告诉我公开测试要验证什么，以及你准备先改哪一处。先给计划，暂时别改代码。

预期：读到 README、公开测试和 `table.py` 的相关正文，指出缺失的列统计上下文及 `_execute_sql_ui()` 的位置。说明公开测试检查 `executeSql`、查询 URL、列顺序和类型、筛选参数。无命令、无写入审批，文件哈希不变。

**2. 执行原始测试。** 在同一对话切到「执行需批准」，发送：

> 按刚才的计划，先运行 README 里的测试命令。只运行测试，不改文件。告诉我用例名、失败断言和退出码。

预期：请求批准测试命令。批准后，真实回执退出码为 1，`test_filtered_page_exposes_statistics_context` 因缺少 `executeSql` 失败。回复能引用这个结果。文件内容不变。若正文说「只有只读权限」，核对本轮保存的模式和实际提供给模型的工具。

**3. 批准变更并重测。** 保持执行模式，发送：

> 根据刚才的失败和 README，只修改 datasette/views/table.py，补齐表格页列统计需要的数据。保留公开测试和 tests/test_candidate.py。修改前让我审批，改完用同一条命令重跑测试，告诉我改了哪里和真实测试结果。

预期：提出目标为 `datasette/views/table.py` 的修改，由测试员批准后写入。网页重新读取和沙箱读取看到同一份新内容。批准重测后真实回执退出码为 0，公开用例通过，只有题目业务文件发生内容变化。

**4. 手动提交。** 在「改动与验证说明」填入「补齐表格页列统计数据，公开测试 1 项通过」，点「提交本阶段」。确认第一题回执和下一题入口。按实际页面等待环境就绪并进入第二题。第二题需要加载自己的 README、起始文件和新 Agent 对话。

## 第二题 · 历史 Bug 修复 · 筛选与分页

如果只负责第二题，用新联测凭证入场。在第一题的「改动与验证说明」填「仅转入第二题验收」，用原始工作区确认提交第一题。等第二题开始，核对标题是「历史 Bug 修复 · 筛选与分页」。只统计第二题的测试和回执。

**1. 只读计划。** 在第二题点「＋」开新对话，选「只读计划」，发送：

> 请读当前工作区根目录的 README.md 和 tests/test_public.py。再用文件搜索定位筛选计数和切换链接相关的代码，并读对应片段。请分别说明翻到第二页后筛选计数为什么会变、切换筛选时为什么可能跳错页，以及你打算先改哪些文件或函数。用中文给出计划。这一轮只读文件，不运行命令，不修改文件。

预期：区分「第二页筛选计数只统计了部分行」和「切换筛选仍带上一组的翻页游标」两种现象。定位到本题的相关源码或函数。无命令或写入，不混入第一题的代码与对话。

**2. 执行原始测试。** 在第二题同一对话切到「执行需批准」，发送：

> 在当前工作区根目录请求运行 README 里的命令 `python -m unittest discover -s tests -p "test_*.py" -v`。等我批准后执行。这一轮不改文件。用中文分别告诉我两个公开用例的失败断言和实际退出码。

预期：批准后，真实回执退出码为 1，`test_second_page_counts_all_matching_rows` 和 `test_toggle_restarts_at_first_page` 失败，能看到计数或链接断言和对应输出。

**3. 批准变更并重测。** 保持执行模式，发送：

> 根据刚才两个公开测试的失败，按 README 修复筛选计数和切换链接。业务代码只修改 datasette/facets.py、datasette/views/table.py、datasette/views/table_extras.py 中实际需要的文件。保留公开测试和 tests/test_candidate.py。请提交实际的修改审批。批准并应用后，用刚才同一条命令重跑。用中文列出实际修改的文件、每项公开测试的结果和退出码。如果还有失败，请贴出失败断言。

预期：审批和写入只涉及该题允许的业务文件，实际回执与可重新读取的文件版本一致。批准重测后退出码为 0，两个公开用例通过。Agent 能说明统计覆盖全部匹配行、切换链接从第一页开始。

**4. 手动提交。** 两个用例通过后，填入「修复筛选统计和翻页链接，公开测试 2 项通过」，点「提交本阶段」并确认。刷新页面，确认第二题回执可恢复，已交卷阶段无法继续运行 Agent 或修改工作区。验收反馈附原始和最终测试输出、改动文件及第二题回执。若某步失败，附运行 ID 和报错。

## 前端改动 · Agent 回复展示 Markdown

在 R2 工作台右侧，把 Agent 的回复按 Markdown 渲染。优先覆盖段落、标题、粗体、有序及无序列表、行内代码和围栏代码块。窄侧栏内的长代码块独立横向滚动，便于完整读取和复制。回复内的原始 HTML 按文本显示或过滤，审批卡、工具日志和状态标签保留各自的展示。

验收时用第二题的只读计划回复检查列表、粗体、文件路径和多行代码。若这轮回复缺少某种格式，在新对话发送「请用 Markdown 写一段示例，包括标题、两条列表、粗体、行内文件路径和一个三行 Python 代码块」。刷新并恢复同一对话后，核对历史回复的格式一致。回复展示与第二题的测试结果分别记录。

## 如何判通过和安排修复

| 场景 | 通过证据 | 失败时先查 |
| --- | --- | --- |
| 只读转执行 | 同一对话保留计划，执行轮确实获得命令与写入工具 | 前端请求的模式、后端策略快照、实际给模型的工具。跨轮失败时查压缩检查点和新轮的关联 |
| 模型答复 | 能发出实际工具请求，测试结论可对应到真实回执 | 模型是否拿到了本轮工具。拿到了仍声称无权限、只给建议或重复搜索时，对照同一模型和工具协议 |
| 审批 | 等批准时没有写入或执行。另开一轮拒绝一次测试命令，确认未执行，再显式重试 | 审批与当前请求的绑定、拒绝状态回传、是否偷偷重新发同一请求 |
| 执行与保存 | 有真实退出码和输出，文件改动落在同一工作区。公开测试哈希原样 | 命令工作目录、文件版本、工具回执、编辑器与沙箱是否读写同一份文件 |
| 停止与恢复 | 另起短用例，在运行中断开浏览器连接再恢复，仍能看到同一个运行。点停止后重复查仍已停止，迟到结果不能写文件 | 后端是否独立推进、事件恢复和命令取消是否生效 |
| 交卷 | 手动交出两题，刷新仍有两个回执，上一题的运行和文件不能串到下一题 | 阶段归属、工作区冻结、切阶段时的 Agent 关闭和状态恢复 |

后台显示「已完成」只代表模型结束了回复。执行步骤以同一轮的审批、操作回执、测试输出和真实文件改动为准。修一个阻塞点后，用原输入和原先的条件重放该步，最后用新工作区从第一步再走一遍。记录平台提交、题目镜像、模型、运行 ID、审批结果、测试退出码、改动文件及交卷回执。

后端可以修现有运行时，也可以换成熟 Agent 内核。两条路线使用相同题面、工具权限和通过标准。选复用路线时，先验证新内核能在现有考生沙箱里受控读、改、跑，能把审批和真实工具结果接回页面，并能随阶段结束停止。两题均通过时，可以确认基础 Agent 流程可用，题型设计即可用这套能力推进。
