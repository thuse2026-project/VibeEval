# VibeEval 多阶段考试适配方案

以新增多阶段模式承接四阶段考试，复用现有入场身份、Agent 核心、编辑器和沙箱操作，新增考试编排与阶段级数据归属。实现顺序为流程与权限底座、文字答卷、代码答卷、评分发布。

## 开发基线

2026-11-09 已核对本地与远程分支，开发分支为 `feat/multi-stage-exam`。

- 本地工作区原先干净，`feat/agent-integration@241c05e` 与远程一致；执行推送返回 `Everything up-to-date`。
- 本地 `main` 从 `ab35b31` 快进到远程 `341d070`，补齐 47 个提交。
- 新分支从最新 `main` 建立，合入 Agent 分支的 13 个功能提交。主线侧独有的是一期合并提交；合并后的文件内容与原 Agent 分支一致。
- 其余有 upstream 的本地分支与远程一致；`review/workspace-writer-cleanup` 的提交已存在于远程 `codex/sandbox-lifecycle`，无遗漏的本地功能提交。

需求输入为《VibeEval 多阶段考试第一版方案》。其中时间、分值、文字限额和预算作为版本化配置；以下为结合当前代码的实施提案。本轮新增方案与入口，考试业务代码尚未改动。

## 考试流程

一场考试包含四个顺序阶段，第一阶段分为探索和独立答题。阶段结束后不能返回读取详细材料；同一阶段的冻结笔记可从探索带入答题。

| 阶段与环节 | 默认时间 | 仓库 | 考生能力 | 提交内容 |
| --- | --- | --- | --- | --- |
| 一 探索 | 20 分钟 | A 正确基线 | 浏览、搜索、只读 Agent、编辑笔记 | 环节结束时冻结笔记 |
| 一 独立答题 | 15 分钟 | 同一 A 基线 | 浏览、搜索、读笔记、填写五题 | 文字答卷 |
| 二 独立审阅 | 20 分钟 | A 独立缺陷版本 | 浏览、搜索、填写缺陷报告 | 结构化文字答卷 |
| 三 功能实现 | 50 分钟 | B 功能缺失版本 | 编辑、终端、读写 Agent | 代码快照与实现说明 |
| 四 缺陷修复 | 40 分钟 | B 独立缺陷版本 | 新工作区、新 Agent、编辑与终端 | 代码快照与修复说明 |

作答共 145 分钟。三个阶段间过渡各默认 60 秒，在上一答卷安全固定且下一环境准备好后计时；可以提前开始，离线也会自动推进。探索到答题没有过渡休息，撤权完成后启动独立的 15 分钟计时。后台评分不占下一阶段时间。

各阶段按 100 分保存，整场默认权重为 20%、20%、30%、30%。考试完成与成绩发布分开；未齐分或待复核时不生成最终总分。

## 当前代码需要处理的边界

| 已核实的实现 | 适配方式 |
| --- | --- |
| [Submission](../backend/app/db/models.py) 对 `session_id` 及 `exam_id + candidate_id` 唯一 | 新增阶段答卷表，以 `stage_attempt_id` 唯一；旧提交约束保留 |
| 同文件版本按 `session_id + path` 区分 | 新模式使用 `workspace_id + path`；阶段三、四同路径也有各自版本 |
| [SessionLifecycle](../backend/app/db/lifecycle.py) 同时持有整场状态、时限和一个沙箱 | 新增考试、阶段、环节编排；入场会话继续承担身份与浏览器恢复 |
| [WorkspaceReader](../backend/app/workspace/service.py) 读文件也要求 `require_writable()` | 分开读取和写入权限；只读阶段不能依赖可写状态才能浏览 |
| [文件策略](../backend/app/workspace/files.py) 和 [沙箱模板](../backend/app/sandbox/booking_template.py) 绑定预约样题 | 按冻结题包提供发布清单、可写范围、镜像和读取适配器 |
| [Agent 存储](../backend/app/agent_integration/store.py) 与材料按整场 `exam_session_id` 隔离，支持同考试跨对话读取 | 引入环节级 Agent scope；同步收窄历史、材料、引用、上下文及事件读取 |
| [Agent 装配](agent-integration-handoff.md) 默认关闭，没有常驻 worker，现有预算主要约束单次 Run | 增加考试业务装配、持久运行调度和阶段累计预算；订阅事件不承担推进职责 |
| [入场 Cookie](../backend/app/exams/router.py) 的 Path 是 `/api/v1/sessions` | 增加服务端鉴权交换，给 v2 单独命名的 HttpOnly Cookie，Path 为 `/api/v2` |
| [缓存中间件](../backend/app/main.py) 仅覆盖现有 v1 私有路径 | 扩展 v2 私有响应的 `Cache-Control: no-store` |
| [当前评测](../backend/app/admin/evaluation.py) 使用固定预约题及 60 分公开测试规则 | 新增按题包和评分版本执行的评测；原评分语义保留给旧考试 |

新增 API 和页面同时上线时，必须阻止多阶段考生通过 v1 准备、开考、文件、终端、Agent 或交卷接口进入旧业务路径。旧模式选择由服务端冻结的配置决定，客户端不能自行切换。

## 数据归属和兼容方式

新增业务模块建议放在 `backend/app/exam_flow/`，前端放在 `frontend/src/candidate/exam/`。数据库模型和迁移仍统一维护，不复制入场鉴权和 Agent 核心。

| 对象 | 归属与主要约束 |
| --- | --- |
| `ExamDefinitionVersion` 与 `StageDefinition` | 固定四阶段、五环节、时长、权重、题包、模型与预算；开始后不可原地替换 |
| `ExamAttempt` | 关联现有入场会话与冻结配置；一期每个入场会话最多一个多阶段 attempt |
| `StageAttempt` | 归属 attempt；`attempt_id + ordinal` 唯一，记录准备与封存错误、重试信息 |
| `PhaseAttempt` | 归属 stage；记录开始、截止、关闭原因与 `permission_epoch` |
| `WorkspaceInstance` | 归属阶段；绑定题包摘要、存储或沙箱资源；第一阶段两环节共用只读基线 |
| `WorkspaceFileVersion` | `workspace_id + path` 唯一，沿用版本冲突及摘要观察机制 |
| `AnswerDraft` 与 `NotesDraft` | 归属环节和题目或条目，保存版本、内容及服务端接收时间 |
| `StageSubmission` | `stage_attempt_id` 唯一；固定文本、笔记引用、说明或代码快照，保存摘要与关闭原因 |
| `AgentScope` | 绑定入场身份、环节、工作区与授权版本；对话、材料、操作均按此范围访问 |
| `EvaluationRun` | 绑定不可变答卷及题目、测试、规则、模型版本；允许重评，保留原结果 |
| `ExamEvent` 与持久任务 | 状态变更与事件在同一事务提交；关闭、准备、封存、评分可重试并有租约 |

整场、阶段、环节和评分分别维护状态，采用输入方案中的四组状态；基础设施错误放在错误字段和任务状态中，不当作考生失败。成绩另设发布状态。

Agent 存储适配单独安排迁移：新增显式 scope 外键，逐一处理现有 Agent 表的复合外键、唯一键及快照一致性校验。旧记录回填 legacy scope，scope 标识保留原会话编号，使旧快照中的 `scope_id` 仍有效；v1 通过 legacy scope 适配器工作。v2 使用环节 scope，不能把 `phase_id` 直接塞入仍引用 `exam_sessions` 的字段。

第一、二阶段可使用服务端不可变题包的只读读取器，无需为了浏览代码启动可执行沙箱。第三、四阶段各分配独立 gVisor 工作区。两类读取器实现一致的目录、读取、搜索接口，均按当前环节检查材料可见性。

迁移从当前 Alembic `0010` 之后追加，拆分考试底座、Agent scope 和答卷等批次。旧考试记录不转换成四阶段记录。模式路由隔离与新表先上线，再开放新场次；已经开始的 attempt 继续绑定原配置。

## 权限与后台推进

统一由 `PhaseAccessPolicy` 生成当前能力，输入包括考生身份、attempt、phase、workspace、服务端时间和授权版本。HTTP、WebSocket、Agent worker 和后台任务都使用同一策略。

能力至少包含代码读取、代码写入、终端、Agent、答案编辑、笔记读取与笔记编辑。前端能力仅决定布局，后端在每次操作时核验。Agent 工具集合是环节白名单与服务端策略的交集，浏览器只能收窄。

文件、命令、批准和模型运行均绑定 `phase_id + permission_epoch + workspace_id`。关闭环节时先持久化撤权并递增 epoch，再取消旧请求；任务取出、工具执行前及结果写回时都重新核验。旧批准不能重新授权；迟到的模型回复可保留审计记录，但不能作为下一环节的答案、材料或继续调用工具的依据。

权限检查覆盖 Agent 的历史、对话列表、材料、引用解析、上下文预览、跨对话工具和 SSE。只关闭消息发送会留下读取入口。v1 也须识别多阶段会话，拒绝旧路径绕过。

状态变更先锁定 attempt，再按固定顺序处理 stage 和 phase，数据库保证同一 attempt 最多一个有效作答环节。状态版本避免旧页面推进，数据库唯一约束保证最终答卷唯一；外部操作采用持久任务和租约，数据库锁中不等待无界模型调用。

后台扫描处理截止、准备、封存及过渡；每次前台请求同时检查截止并触发相同的幂等推进。请求补查不能让浏览器成为唯一调度器。任务迟到时沿用已持久化的截止与过渡时间，不因重试重新发放时长；需要撤权或环境准备的步骤，以实际成功记录决定何时开放下一环节。

阶段预算跨所有对话累计，发送前在事务中预留，回执后核算，未知结果保留预留并进入核查。新建对话不能重置预算；预算耗尽只停止新 Agent 调用，考生仍可在截止前自行完成。

## 关闭环节与固定答卷

探索转答题时，先提交 `closing` 与新 epoch，停止 Agent 推进和事件读取，处理正在运行的请求，冻结已保存笔记；完成后一次性开放五题并写入答题起止时间。任何一步失败都保持关闭入口，恢复任务继续完成切换。

文字草稿默认停输 1 秒及失焦保存，携带 `expected_revision`。服务端以版本条件更新，冲突返回最新版本，不能让迟到请求覆盖新答案。前端每题维护保存队列；主动提交先等待保存完成，到时只封存服务端已接收内容。字符限额统一按 Unicode 码点计算，前端使用 `Array.from(text).length`，后端使用 Python `len(text)`，不自动归一化内容。

代码提交沿用现有“先持久化写入屏障，再固定工作区”的机制，但编排对象改为阶段：

1. 阶段进入 `sealing`，撤销文件、终端与 Agent 权限，拒绝新写入，排空已接受的保存。
2. 由沙箱控制层暂停整个工作区容器，并停止或冻结所有相关执行 helper 和 writer；不能用关闭 WebSocket 代替冻结进程。
3. 导出并校验阶段代码快照，原子提交唯一回执、内容摘要和后续评分任务。
4. 快照提交成功后才允许开始下一阶段过渡；资源清理另行重试，不撤销已提交回执。

导出或持久化失败时保留冻结状态，重试同一阶段，不重新开放编辑。手动提交、到期任务和网络重试统一查询 `stage_attempt_id` 的已提交回执；已成功的重复提交优先返回原回执。幂等键用于识别请求，不能代替阶段唯一约束。

## 接口与前端适配

沿用输入方案的 `/api/v2` 命名空间。v1 入场成功后，通过受现有 Cookie 和来源头保护的交换入口建立 v2 访问凭证；JS 不读取或复制身份秘密。v2 每次仍复核浏览器绑定和 attempt 归属，标识本身不是凭证。

| 接口组 | 职责 |
| --- | --- |
| `GET /api/v2/attempts/current` | 恢复考试、当前阶段、环节、时限、过渡、状态版本和能力 |
| `POST /api/v2/attempts/{id}/start` | 环境就绪后开始第一阶段 |
| `GET /api/v2/stages/{id}` 与 `POST .../start` | 当前阶段状态与过渡期提前开始 |
| `POST /api/v2/phases/{id}/finish` | 提前结束探索，执行统一撤权切换 |
| `GET .../phases/{id}/questions` | 当前环节可见的题面；评分材料使用独立存储与返回模型 |
| `PUT .../phases/{id}/answers/{item_id}` 与 `PUT .../notes` | 带版本的答案和笔记保存 |
| `POST .../stages/{id}/submit` 与 `GET .../submission` | 发起封存和查询不可变回执；封存未完成返回进行中状态 |
| `GET .../attempts/{id}/events` | 以持久游标读取考试事件，重连后重新获取状态 |
| `.../phases/{id}/agent/...` | 复用 Agent 原子能力，补齐对话、运行、交互、材料及事件接口 |
| `.../workspaces/{id}/files` 与终端接口 | 解析阶段工作区，检查当前 phase 和 capability |

开始、结束探索和提交请求带状态版本及幂等键；答案和文件另带内容版本。成功请求的重放先查原结果，再检查当前状态版本。统一返回 `PHASE_CLOSED`、`CAPABILITY_DENIED`、`REVISION_CONFLICT`、`SUBMISSION_IN_PROGRESS`、`WORKSPACE_UNAVAILABLE` 等明确错误码。

前端新增考试容器，顶部统一显示阶段、环节、服务端倒计时、保存状态；中部根据能力组合代码浏览、Agent、笔记、答题表单或编辑终端。复用现有 [CodeEditor](../frontend/src/shared/components/Editor.tsx)、FileTree、TerminalGateway 和保存队列机制。

现有 [CandidateWorkspace](../frontend/src/candidate/workspace/CandidateWorkspace.tsx) 将单场状态、一个文件列表和一组草稿绑定在一起，不宜直接累加四阶段判断。新容器按 `workspace_id` 管理编辑器模型、缓存、请求及保存队列；切换工作区时销毁旧模型并取消旧读取，防止同路径文件、Undo 和迟到响应串入下一阶段。只读阶段默认选择首个可见文件，不能沿用“首个可写文件”的初始化条件。

提交后的页面展示阶段回执与过渡状态；四阶段完成后显示等待成绩发布。阶段材料接口设置禁止缓存，切换时清空当前可访问内容；服务端隔离不能依赖清理浏览器缓存实现。

## 评分与题包

题包发布时固定考生材料和服务端评分材料的摘要。前者包含题面、代码、公开测试与允许阅读的资料；后者包含隐藏测试、参考修复、要点和缺陷说明。评分材料不进入候选镜像、浏览器响应或 Agent 来源注册表。

第一阶段按五题要点评分，只读取该题答案、题面和受控代码证据。第二阶段按已验证缺陷评分，预设以外的有效发现进入人工复核，不自动加分或判错。第三、四阶段在独立环境运行可信测试，按业务分组计分，结合有证据的代码审阅。

按输入方案配置第三阶段 50/20/15/15、第四阶段 45/25/20/10 的分项；第四阶段原缺陷仍可复现时上限 50 分的规则必须向考生公开。平台环境失败进入重试或复核，不作为考生零分。

重评只新增 `EvaluationRun`，人工调整保存原评分和理由；成绩齐全且复核完成后由考官发布。评分任务与答卷事务通过持久任务衔接，避免“答卷已提交但评分任务未创建”；评分失败不阻塞下一阶段。

## 实施批次与验收

| 批次 | 主要交付 | 完成条件 |
| --- | --- | --- |
| M1 流程和权限底座 | 冻结配置、attempt/stage/phase、鉴权交换、模式隔离、统一 policy、持久事件与截止调度 | 状态能恢复；并发只能推进一次；离线不重置时间；v1 不能绕过 v2 |
| M2 文字阶段闭环 | Agent scope 迁移、A 只读题包、探索与答题切换、笔记和五题、审阅报告、文字回执 | 用真实只读 Agent 完成第一阶段；到时撤权；保存乱序不丢新答案；第二阶段不可访问正确基线 |
| M3 代码阶段闭环 | 题包驱动沙箱、工作区版本、Agent 调度与阶段预算、阶段快照、三到四阶段切换 | 新工作区、新对话；冻结后所有写入停止；重复提交同一回执；失败保持冻结 |
| M4 评分和考官端 | 通用评测、文字评分、复核、补时留痕、重评与发布 | 分数证据可追溯；异常分类准确；答卷不可被重评改写；未发布不泄露成绩 |

第一批编码从 M1 的模型迁移、鉴权桥接和 `PhaseAccessPolicy` 开始，随后接数据库事务与后台推进。M1 同时做两项技术验证：使用延迟模型回复验证撤权后无法继续读取或操作；使用持续写文件的沙箱进程验证冻结后摘要稳定。测试替身用于单元验证，真实 gVisor 验证须在具备环境时单独执行并记录结果。

验收使用可控制的服务端时钟和独立 PostgreSQL，覆盖保存与截止竞争、手动与自动提交竞争、过渡与提前开始竞争、多 worker 重复领取、任务中断恢复和提交后断线。浏览器验收覆盖刷新恢复、旧标签页、只读布局、保存失败、同路径跨工作区缓存及阶段进度。

上线试测必须跑通一套冻结样卷的全部四阶段，并确认：探索对话在答题期不可读；未来题目不可提前读；第三阶段文件、终端和对话不能进入第四阶段；冻结导出失败不推进；评分错误不误判考生；旧单阶段考试仍可完成原链路。
