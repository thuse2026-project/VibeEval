# Datasette 两题评分与评阅

每道题独立计分：客观功能与回归测试 **70 分**，考官评价 **30 分**。未评显示未评；两部分都完成后才显示总分。当前没有自动主观评分，也不将模型自报“完成”或考生终端的输出换算成分数。

## 分值

### 业务拓展：补齐列统计

| 客观分组 | 分值 |
|---|---:|
| 公开基础场景：带筛选的表格页提供统计上下文 | 10 |
| 列结构：顺序、声明类型、rowid、生成列及界面隐藏列 | 15 |
| 筛选条件能够驱动全部匹配行的实际统计查询 | 15 |
| 无 SQL 权限时不暴露统计入口及数据 | 10 |
| 既有业务筛选与分页行为不回归 | 20 |

人工项：新增测试 15 分，实现质量与说明 15 分，按下表独立给分。满分/部分分/零分是锚点，其他中间分须说明依据；不按测试数量给分。

| 小项 | 满分 | 满分条件 | 部分分条件 | 零分条件 |
|---|---:|---|---|---|
| 新增测试：有效断言 | 5 | 核对具体业务结果/错误行为，失败能定位原因 | 2.5：有业务断言但关键结果遗漏 | 无新增验证、仅复制、恒成立或期望错误 |
| 新增测试：关键边界 | 5 | 覆盖重要新边界或组合并能说明理由 | 2.5：有价值新场景，但关键边界缺失 | 无新增场景或与任务无关 |
| 新增测试：实际检错 | 5 | 正确测试能抓住功能缺失/错误实现，有运行或逻辑依据 | 2.5：只能发现部分问题，断言过宽 | 无新增检错内容或测试自身错误 |
| 实现质量：接口与异常 | 4 | 接口及异常路径清楚，没有掩盖异常或硬编码伪造结果 | 2：局部处理宽泛或不清楚 | 接口混乱、吞异常或硬编码规避要求 |
| 实现质量：修改范围 | 4 | 修改集中，无无关重写或破坏 | 2：少量无关改动 | 大量无关改动，显著增加风险 |
| 实现质量：可维护性 | 4 | 命名和逻辑清楚，合理复用，无明显重复或过度复杂 | 2：局部重复或难理解 | 实现明显难以理解和维护 |
| 实现说明：改动与验证 | 3 | 准确说明实际改动、已做和未做的验证 | 1.5：基本属实但不完整 | 无有效解释或明显与事实不符 |

### 历史 Bug 修复：筛选与分页

| 客观分组 | 分值 |
|---|---:|
| 公开场景：跨页筛选计数覆盖全部匹配行 | 20 |
| 公开场景：切换筛选从第一页开始 | 25 |
| 排序与业务筛选组合 | 10 |
| 数组、日期筛选及重复参数的切换 | 10 |
| 原有无筛选分页行为不回归 | 5 |

人工项：新增回归测试 20 分，解释与实现质量 10 分。若两个公开原始缺陷中任一个仍可复现，本题最终总分上限为 50 分；页面明确显示封顶原因。此规则沿用现有题面。

| 小项 | 满分 | 满分条件 | 部分分条件 | 零分条件 |
|---|---:|---|---|---|
| 新增回归测试：有效断言 | 5 | 新增断言核对业务结果/错误行为，失败可定位 | 2.5：关键断言遗漏或不清楚 | 无有效新增验证、复制或期望错误 |
| 新增回归测试：关键边界 | 5 | 覆盖重要新边界/组合并说明理由 | 2.5：只有部分重要新场景 | 无新增场景或与任务无关 |
| 新增回归测试：复现原缺陷 | 10 | 两个缺陷均有正确的新增检错内容，各 5 分 | 5：仅覆盖一个原缺陷 | 未新增有效复现，复制或期望错误 |
| 根因解释 | 4 | 准确解释两个问题的因果关系，有代码/测试证据 | 2：仅一个根因正确或因果链遗漏 | 缺失或与实际代码矛盾 |
| 修改范围与修复质量 | 3 | 针对根因、范围合理、逻辑清楚，无无关破坏 | 1.5：局部重复、不清楚或无关改动 | 掩盖现象、硬编码绕过或大量无关破坏 |
| 验证说明 | 3 | 准确说明复现、修复、验证结果及未验证内容 | 1.5：属实但不完整 | 缺失或与真实结果矛盾 |

各客观分组采用通过得该组分数、失败得零分；当前不在一个分组内部再次按断言拆分。公开测试的代码允许考生阅读，私有测试代码与参考实现不提供给考生。

### 已确认的给分边界

- 复制公开测试或只改名、无新增验证的部分，不得新增测试分。确有新的输入、边界或断言时，仅评价新增内容；自动相似提示不是语义判定，需核对测试夹具。
- 正确的测试发现交卷代码仍有 Bug 时，测试质量可以得分，功能另评；历史 Bug 题的 50 分上限仍生效。不能把所有测试失败都归为“测试写得差”。
- 提交说明、代码注释、测试注释中的有效解释均可作证据；只扣对应缺失项，不因漏填提交说明连带扣测试和实现质量。
- 功能结果由 70 分评价；30 分评价新增验证和实现/解释质量，不因同一条功能测试失败机械地再次扣所有质量项。
- 每小项独立填写依据，即使零分也说明缺失之处；测试项非零时须确认其对应真实新增验证。

### 新增测试双版本证据

“运行新增测试对照”把封存的同一份 `tests/test_candidate.py` 分别注入原始代码与交卷代码，在两个新的 gVisor 容器执行；不运行公开测试，且不会改动原答卷。逐条展示通过、断言失败、运行错误、跳过、预期失败和意外通过。超时/进程异常或平台失败不会自动变成测试质量零分。输出限长，截断会标记；最多观察 200 条测试/子测试记录，超出时标为不完整，不冒充完整逐条证据。

| 观察结果 | 如何理解 |
|---|---|
| 原始失败、交卷通过 | 可能抓住了已修复的问题，仍需核对期望是否正确 |
| 两边失败 | 可能交卷代码仍有缺陷，也可能测试错误，核对失败原因；不能直接判测试零分 |
| 两边通过 | 可能检查正常行为或额外边界；不能据此直接判无效或证明其检错能力 |
| 跳过、无测试、运行错误 | 不算测试通过；查看代码及夹具原因，不自动折算分数 |

这些是**不受信任的考生程序执行证据**，考生可以操纵自己的测试和结果；它不替代宿主可信断言，也不自动产生分数。疑似复制提示仅通过语法树比较测试正文，不执行考生代码；改名和注释不影响提示，夹具变化仍需考官核对。相似检查跳过大文件或无效语法时不作结论。

证据绑定答卷摘要、评分规则摘要和测试文件摘要；重测不改人工评分，也不覆盖页面未保存草稿。未完整完成时保留上一次完整证据，并单独提示最新运行问题。

### 规则版本与旧记录

小项细则使用 `*-70-30-v2` 题包。旧规则下的两大项评分与客观结果保留在原规则摘要目录，页面提供只读历史；不自动转换为新小项。启用新版题包后，当前规则先显示未评，需重新执行客观评测及按小项评阅；下一轮正式出题应将此公开细则同步到考生题面，已开始的考试不修改其固定材料。

## 考官操作

1. 用已有考官账号登录，在导航选择“多阶段评阅”（`/admin/r2`）。每个阶段是一份独立答卷。
2. 打开“查看与评分”，查看考生说明、改动文件及固定代码快照。
3. 点击“开始客观评测”，平台对封存代码重新执行可信测试，显示各组结果及 70 分中的得分。重新评测仍使用同一份封存代码。
4. 运行新增测试对照，核对测试、代码和注释；按每个小项填写分数及依据，再保存。先核对是否有真实新增验证、断言是否正确，再结合两次运行结果和实际修改评价；测试数量本身不直接得分。
5. 刷新后应恢复已保存结果。并行评阅发生版本冲突时，不覆盖别人已保存的评分；使用“载入已保存评分”核对后重填。重新客观评测或网络重读会保留当前页面尚未保存的人工草稿，离开页面或整页刷新前请先保存。

平台环境、可信夹具或适配器发生异常时显示未评，不计零分；重测失败也不抹掉上一次成功的客观结果。考生行为不符合断言、代码无法导入、请求报错或超时，属于对应分组未通过。修改受保护文件或版本不匹配时不发布分数，交由维护者核查。

## 可信执行边界

- 从已交卷、已封存阶段读取固定快照；核对原题只读文件和完整文件集合。
- 使用该阶段记录的不可变镜像 ID，在新的 gVisor 容器内运行考生 Datasette。禁网、只读根目录及答卷卷，UID 1000，512 MiB、0.5 CPU、64 PID；临时数据放在独立 `/tmp`。
- 可信测试和断言留在维护者侧；仅将测试请求、临时 SQLite 夹具和响应传入隔离进程。宿主机不导入或执行考生模块；考生自写测试只在双版本证据的独立受限容器内执行。
- 客观结果和人工评阅绑定答卷快照摘要与评分规则摘要。记录在既有快照根目录的 `r2-evaluations/`，原子保存；人工评分另带修订号、评阅人、时间和依据。备份须覆盖该目录。
- 当前沿用预览服务的单进程考官会话及评分互斥锁，适用于小组联测。多 API 进程部署前须把评分写入/互斥迁入共享事务存储，不能直接多开进程。

## 维护者配置

评分题包是私有维护材料，需要从出题负责人取得当前两题的私有测试和起始工作区清单；公开仓库不含参考修复或私有断言。

在有权限的维护环境中，用既有工具生成一次题包：

```sh
cd backend
PYTHONPATH=. python tests/manual/build_datasette_grading_bundle.py \
  --contexts /private/datasette-contexts \
  --private-tests /private/datasette-tests \
  --output /private/datasette-grading-v1 \
  --column-image sha256:<本机列统计镜像ID> \
  --facet-image sha256:<本机筛选分页镜像ID>
```

私有测试目录须包含 `test_column_statistics.py` 和 `test_facet_pagination.py`；由维护者审核后提供，不能接收考生上传文件作为可信测试。输出目录必须不存在，工具校验模块哈希和权重。

在真实 API 进程环境配置 `VIBEEVAL_DATASETTE_GRADING_BUNDLE=/private/datasette-grading-v1`，重启应用。Docker 连接沿用 `SANDBOX_DOCKER_URL`；不用添加模型评分 Key，也没有新数据库迁移。已有考官账号配置仍为 `ADMIN_ACCOUNTS_FILE`。未配置题包时接口返回明确的 503，不回退到示例评分。

后端接口均位于现有考官 Cookie 范围内：

- `GET /api/v1/admin/r2/submissions`：分页列表，可选 `exam_id`。
- `GET /api/v1/admin/r2/submissions/{id}`：固定答卷、分组规则及保存的结果。
- `POST .../{id}/evaluate`：重新评测固定快照。
- `POST .../{id}/review`：保存 `{expected_revision, scores, note}`，冲突返回 409。
- `POST .../{id}/candidate-tests`：执行双版本新增测试对照，不改客观或考官分。

v2 的 `/review` 另要求 `evidence`（逐项依据）及 `novel_tests_confirmed`（测试项非零时确认存在非复制验证）。

所有写请求要求现有 `X-VibeEval-Request: 1` 请求头。客观评测可能耗时，请在超时后重新读取记录核对，勿根据断连推断得分。
