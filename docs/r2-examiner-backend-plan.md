# R2 考官端后端方案

## 当前分支的实现与启动

当前集成版的房间接口沿用本页设计。迁移至 `0016_r2_publication`，配置稳定的 `VIBEEVAL_ROOM_TOKEN_KEY`、考官账号、四题定义与可信评测材料。两条旧分支均曾使用迁移编号 0013，当前迁移会识别房间分支的表结构并补上证据表。四题评分、发布与部署入口见[四题接口](r2-candidate-api.md)。下文的旧房间调分接口用于原评分规则的答卷。

当前沿用全组考官都是管理员的模式。登录考官共享新房间、凭证和复核权限，保留创建者及操作者记录。旧答卷仍在「历史答卷与评分」。归档筛选和创建者独占尚未接入新页面。

实现使用房间随机 ID 和服务端 HMAC 密钥按需派生凭证，数据库继续存认证哈希。考官可展开未认领且未过期的凭证。密钥变更后，原凭证仍可凭数据库哈希认领，但界面无法回显旧值。

新版主观评分接入前，编程题读取现有 Datasette 客观结果与已保存人工评分。缺项显示未评，已有完整基础分才可复核。文字题可以查阅固定答案，自动评分待接入。回放读取存量的对话、审批和操作事件及可用的完整 Agent diff。人工编辑、裸终端动作和旧材料缺失会影响记录完整度。

复用现有考官 Cookie、PostgreSQL 入场、考试流程、固定答卷和评分模块，新增面向房间的查询与创建、授权回放和一次性复核。房间是「一份冻结试卷发给一名考生」的管理视图。前端可独立按下述契约开发，[前端方案](r2-examiner-frontend-plan.md)描述页面。

## 现状与本轮依赖

- `PostgresEntryStore.invite/admit` 已有随机 Token、哈希查验、单次认领与原浏览器恢复；现有考官总览主要读取旧会话和提交。R2 房间状态来自多阶段 attempt，单题提交不等于整场完成。
- 当前考官 R2 读接口主要以 Datasette 单题答卷为索引，支持客观评分、旧人工评分和新增测试证据。四题在线装配与新版 AI 问答、过程分是考生/评分方案的交付依赖。可先接示例契约验证 UI，真实房间以部署中已验证的四题版本为准。
- Agent 已有会话、事件、审批及部分 diff 预览。先核实哪些事件有持久化原文或前后版本，补齐新房间的记录留存。现有裁切预览无法还原全部历史逐次改动。
- 设计默认沿用已定的客观70、问答20、过程10。你这次提到的代码风格如需独立计分，需决定从哪一项划分。房间、列表、成绩详情和回放可并行开发，评分项沿版本展示，复核逻辑以该版本的分数边界为准。

## 房间、入场与凭证

创建时复用 Invitation 和真实认领流程，为其关联稳定 `room_id`、内部考生标识、创建者及冻结试卷引用。重复姓名允许。考官之间是否共享房间待定。本方案暂按「考官管理自己创建的房间，明确授权的管理员可跨房间查看」设计；团队可见范围确定后沿用同一套接口。旧记录沿已授权的历史入口访问。

创建请求传显示名和 UTC 截止时间。服务端检查未来时间，以已注册的四题试卷固定版本随房间持久化。在现有入场链路关联 attempt，同一会话关联一次；若版本加载或关联失败，保留可重试的既定关联，恢复时使用同一冻结版本。凭证到期只影响首次认领，已认领继续使用既有恢复策略。考试时间以多阶段服务端时钟为准。

折叠后还能回看有效 Token，因此新房间在现有查验哈希外，保存由服务端专用密钥保护的加密副本。已有哈希无法反查，旧房间标记不可回显。列表返回状态和稳定房间 ID。仅待入场且未过期时，授权考官可通过单独接口读取明文；到期或认领后回显失效。敏感响应禁止缓存，明文不写日志或 URL。加密及数据库记录与创建同一事务，密钥从部署秘密配置读取。创建按考官和请求键去重，重复请求可找回同一房间；请求键内容冲突返回 409。响应丢失后若已认领或过期，返回既有房间及状态。

状态按服务端权威数据计算。无会话时区分待入场和过期；认领后未开考为已入场；已开考为考试中；attempt completed 且所有回执存在为已完成。准备或封存失败作为当前状态下的说明。评分进度独立计算。

## 前后端契约（拟定）

统一前缀 `/api/v1/admin/r2`。沿用考官认证、浏览器请求头和写请求来源校验。单房间各入口检查同一授权范围；阶段 ID 必须属于该房间。分页统一 `items/next_cursor`，服务端提供稳定排序及游标。

| 接口 | 请求与返回 |
|---|---|
| GET /rooms | 接收 `status,q,cursor,limit`。行含 `id,candidate_name,exam_title,exam_status,grading_status,admission_expires_at,created_at,token_available` |
| POST /rooms | `candidate_name,admission_expires_at,template_version,request_key` → 固定版本、房间摘要、入场入口及可用凭证 |
| POST /rooms/{id}/token | 通过授权后按需回显凭证。410 表示到期，409 表示已认领或旧凭证不可回显，原因用稳定字段区分 |
| GET /rooms/{id} | 房间摘要与四题概览。每题含 `id,title,ordinal,submission_status,grading_status,review_status,score,max_score` |
| GET /rooms/{id}/stages/{stage_id} | 固定题面、答卷，规则版本、分项、证据引用、原分、封顶、最终分、复核状态及可调区间 |
| GET /rooms/{id}/stages/{stage_id}/timeline | `cursor,limit,conversation_id`，返回可回放事件、会话索引、覆盖及缺档说明 |
| GET /rooms/{id}/stages/{stage_id}/diffs/{diff_id} | 返回文件路径、实际写入或审批提案类型、统一 diff、覆盖状态和下一段游标。最终净差异与时间线事件共用该读取格式 |
| POST /rooms/{id}/stages/{stage_id}/review-preview | `score_revision,delta` → 合法性、原分、调整后主观分、封顶前合计和最终试算 |
| POST /rooms/{id}/stages/{stage_id}/review | `action,delta,reason,score_revision,request_key` → 已锁定决定和分数组成 |

建议 `exam_status` 使用 `invited/expired/admitted/in_progress/completed`，`grading_status` 使用 `pending/running/partial/needs_review/failed/scored`，`review_status` 使用 `not_applicable/blocked/open/confirmed/adjusted`。分数未完成用 null。整场有部分题锁定时可在列表用锁定数／可复核题数表达。统一错误至少区分无权限、不可用、已过期、已锁定、分数版本变化及请求键冲突。详情须能读到部分分项，只有成绩齐全且通过验证后可复核。

时间戳使用 UTC Unix 秒，创建后返回 `room`、`entry_url`、可空的 `token`。列表增加默认 false 的 `include_archived`，同时返回 `meta.current_template`（名称、版本、是否可创建）。前端使用该版本创建，冻结前若已有更新返回 `TEMPLATE_CHANGED`，保留输入并核对新版。同键重试优先返回已创建房间。单题详情建议提供 `components[]`，每项含 `key,label,status,score,max_score,reason,evidence_refs`。复核返回 `review`（动作、差值、理由、操作者、时间）及 `score`（客观、原主观、调整后主观、封顶前总分、封顶值、最终总分）。列表与详情注明展示的是原分还是锁定分。

新房间的权限检查覆盖旧总览、按提交 ID 查询和旧评分写接口。凡旧入口仍可访问新房间记录，须走同一检查；本轮切换后也可由旧入口仅服务旧记录。

## 回放与评分证据

回放绑定「房间 → 考试 → 阶段 → 固定答卷与过程截止点」。以服务端落库的事件次序生成稳定游标，跨会话保留顺序和来源。新事件最少提供 `id,occurred_at,conversation_id,actor,kind,status` 及按类型携带的文本或文件变更引用。保留可展示的用户消息、Agent 回复、工具结果、审批与文件变更。去除模型内部思维、系统提示、凭证与私有评分材料。证据引用携带事件 ID，时间线支持 `around_event_id` 定位到对应页，仍受同一阶段访问限制。

用版本内容在后端生成 unified diff，按时间挂到已生效的动作，审批提案单独展示。评估现有编辑器保存和终端写入的采集范围。能关联实际写入者时明确归属；来源不能归属时显示未知。终端等渠道若缺逐写记录，至少在可验证的检查点记录版本差异，标注采集点与归因局限。最终从起始题包和固定答卷生成净差异。历史残缺、裁切范围和未记录渠道返回明确字段；不根据结尾净差伪造中间步骤。

保留可信客观评分及独立 AI 分项。AI 原分、规则、证据和评分修订与固定提交绑定。接口提供评分理由与可定位证据。评分重跑保留历史并尊重已锁定决定。

评分失败由评分维护者沿现有评测入口或评分任务入口按答卷 ID 重跑失败组件。需人工复核的异常由评分负责人核对证据，通过评分服务保存经确认的基础分和理由，并生成新评分修订。上述写入口同样检查授权与复核锁；前端展示当前原因、答卷 ID 及刷新入口。评阅者的一次性确认只在基础分就绪后开放。

## 一次性复核与调分

建议按后两道编程题分别确认，每题各一次。调整落在主观总分，客观组维持原值。整数差值范围为 −10 到 ＋10，并受该题主观上下限约束。例如主观原分 27/30 时最多加 3 分。Bug 题沿用已公布的总分上限，调整先计入未封顶总分，由后端最后应用上限。前两题按其固定评分规则展示，暂按无此调分操作设计。以上是对调分粒度及归属的方案假设，若需要整场一次或四题均可调，实施前同步改规则与契约。

`confirm` 固定原分，差值为 0，理由可选。`adjust` 要求合法非零差值和去空白非空理由。后端持久化原分及输入评分修订、动作、差值、理由、操作者、时间、封顶与最终分。通过数据库事务与按答卷唯一约束保证仅一次成功。网络重试的同键同正文返回原决定，两位考官并行只有一人写入成功。版本变化时以明确冲突提示重新加载，已锁定后旧人工评分写入口和自动重评也不能覆盖生效结果。

## 后端交付顺序与验收

1. 房间接口与认领装配。测试同名考生、服务端时间边界、重复键、两浏览器抢认领、已认领跨过期时间仍正常考试、越权及旧凭证不可回显。完成后与创建表单联调。
2. 房间详情与证据接口。覆盖第一题刚交但整场进行中、整场已交评分未完、评分失败及四题完整结果。用两考生和两阶段验证引用隔离，用已拒和已应用补丁核验证据。回放仍可从持久记录恢复。
3. 复核规则与原子写入。验证超限、空理由、原分确认、封顶、版本冲突、双考官并发、同键重试、重启与重评，并测试历史写接口无法绕过锁定。
4. 交付 OpenAPI 和共享的响应样例：待入场、到期、进行中、已完成待评、四题齐全、一题锁定、历史回放缺档。用真实四题答卷验收「发凭证→进考场→交卷→读分与过程→一次确认」。四题或新版评分尚未上线时，在验收记录中列出真实联调缺口。
